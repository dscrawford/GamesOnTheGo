# Controller diagram UI: research

*2026-08-29 · ~45 sources · Confidence: High on artwork licensing and the layout
algorithm; High on the toolchain (verified locally rather than cited); Medium on
how Steam itself does it (well-supported inference, not a verified fact).*

Research for a UI screen showing, per platform, a gamepad diagram with leader
lines from each button to a label giving what it maps to — the bindings
`gotg pads` already writes into ares' `settings.bml`.

## Executive summary

**The artwork does not exist and has to be drawn.** This is the load-bearing
finding, and it is the opposite of what the glyph-pack landscape suggests. Every
well-known CC0 input-prompt pack — Kenney, Xelu, `controller_icons` — ships
*individual button glyphs*, not controller *bodies*, and none of them covers a
retro console at all. Wikimedia Commons has exactly two usable CC0 controller
bodies (SNES, Game Boy) out of the six shapes this repo needs, and both were
found on inspection to be unsuitable as-is. libretro's per-console overlays,
the obvious "surely they have this" source, contain no console shells — only
abstract buttons, a posture that is itself the correct model to copy.

**The pipeline is settled and verified end to end.** Author each controller as
an SVG carrying invisible `anchor-*` circles, rasterise at build time with
`resvg`, and emit a normalised anchor manifest from the same derivation. The
runtime stays pygame-plus-PNG with no SVG dependency at all.

**The layout algorithm is a solved problem with a provably optimal answer at
this size.** Sorting anchors by y within each side simultaneously minimises
total leader length *and* guarantees zero crossings. It is ~120 lines, O(n log n),
and deterministic — which matters more than optimality here, because a
controller-navigable UI must not reflow.

## 1. Artwork: why it has to be drawn

### The glyph packs are the wrong shape of asset

| Pack | Licence | Attribution | Controller *bodies*? | Retro consoles? |
|---|---|---|---|---|
| [Kenney Input Prompts](https://kenney.nl/assets/input-prompts) | CC0 | No | **No** — glyphs only | GameCube/Wii glyphs, no bodies |
| [Xelu's Free Prompts](https://thoseawesomeguys.com/prompts/) | CC0 | No | Xbox One, PS4, PS5 only | **None** |
| [rsubtil/controller_icons](https://github.com/rsubtil/controller_icons) | MIT (code), CC0 (art) | No | No | None |
| [Controllercons](https://controllercons.github.io/) | SIL OFL 1.1 | Font rules apply | No (icon font) | No |

Xelu's pack does contain body "Diagrams", but only for Xbox One / PS4 / PS5
([mirror README](https://github.com/DJLink/Xelu_Free_Controller-Key_Prompts)),
and its `Others/` tree has no SNES, N64, Game Boy, Mega Drive or GameCube
entry. A [community SVG conversion](https://github.com/haaldor/Xelu_prompts_SVG)
exists but carries a font trap — its Steam Deck glyphs embed COCOGOOSE, which is
free for personal use only.

### Wikimedia Commons: two of six, and neither is drop-in

| Console | File | Licence | Verdict |
|---|---|---|---|
| SNES | [`SNES controller.svg`](https://commons.wikimedia.org/wiki/File:SNES_controller.svg) | **CC0** | Best available; needs rework (below) |
| Game Boy | [`Gameboy.svg`](https://commons.wikimedia.org/wiki/File:Gameboy.svg) | **CC0** | Usable, stylised |
| Generic pad | [`Retro gamepad.svg`](https://commons.wikimedia.org/wiki/File:Retro_gamepad.svg) | **CC0** | Usable as an NES stand-in |
| GameCube | [`GCController Layout.svg`](https://commons.wikimedia.org/wiki/File:GCController_Layout.svg) | CC BY-SA 3.0 + GFDL | **Reject** — copyleft |
| N64 | — | — | **Nothing.** SVG-filtered search returns zero |
| Mega Drive | — | — | **Nothing.** Category holds two generic Noun Project icons |

**I downloaded and parsed all three CC0 files.** None has a single semantic
button id — every id is Inkscape autogenerated (`path3157`, `rect6155`,
`linearGradient4966`). Worse for a diagram:

- `SNES controller.svg` — 29 `linearGradient`, 16 `radialGradient`, 8
  `feGaussianBlur` filters, and **6 `flowRoot` elements**. `flowRoot` is
  Inkscape-only SVG 1.2 flowed text that resvg and browsers do not render.
- `Gameboy.svg` — 78 paths, 21 gradients, a blur filter.
- `Retro gamepad.svg` — 3 blur filters, 6 gradients.

So even the two "usable" files would need every button hand-identified and the
gradient/filter styling stripped to read as a flat diagram — which is most of
the work of drawing one, without the licence and trademark control you get by
drawing it.

### The sources that look promising and aren't

- **libretro `common-overlays`** — CC BY 4.0 (attribution required), and it
  *does* have `snes/`, `n64/`, `genesis/`, `gameboy/` folders. But inspecting
  [`gamepads/snes/img`](https://github.com/libretro/common-overlays/tree/master/gamepads/snes/img)
  shows 29 PNGs of individual buttons and RetroArch function icons — **no
  console shell**. RetroArch named folders after consoles and drew generic
  buttons. That is a deliberate posture, and it is the one to copy.
- **Steam / Valve glyphs** — the Steam Input API returns "a local filepath …
  from Valve's official image set (located in the Steam client's install
  folder)" ([Steamworks](https://partner.steamgames.com/doc/api/isteaminput)).
  That is a runtime lookup inside an installed client, not a redistribution
  grant. Treat as prohibited.
- **SVG Repo** — per-icon licences, and the terms forbid redistributing
  material "in a similar way to SVG Repo website as it is"
  ([licensing](https://www.svgrepo.com/page/licensing/)).

### CC BY-SA and trademark

Two separate issues, both pointing the same way.

**Share-alike.** Recolouring, restyling, adding callout lines or splitting a
BY-SA SVG into per-button paths is *Adapted Material*, so the result must ship
BY-SA with attribution ([CC FAQ](https://creativecommons.org/faq/)). That is
exactly what this feature would do to it. For this repo, BY-SA controller art
is a no.

**Trademark is not covered by any of it.** CC is explicit that its licences are
copyright licences only and "do not license trademark or patent rights"
([CC FAQ](https://creativecommons.org/faq/)). A CC0 SNES SVG frees the
*drawing*; it says nothing about Nintendo's rights in the *shape*. Nintendo
holds a registered configuration mark on the Game Boy's form
([thatsatrademark.com](https://www.thatsatrademark.com/blog/nintendo-handheld-consoles)).

The practical read: a simplified, unbranded, non-photorealistic outline in a
non-commercial FOSS launcher is low risk and matches decades of unchallenged
practice. Risk rises with logos and wordmarks, photorealism, or monetisation.
Mitigation is what RetroArch does — abstract line art, no marks, and a
trademark disclaimer. Drawing it ourselves is what makes that posture available.

**Verdict: draw six flat SVGs in-house, CC0 them, seed SNES and Game Boy from
the Commons CC0 files.** It is the only route that gets licence purity,
guaranteed per-button ids, and trademark distance at once.

## 2. Pipeline: authored SVG → build-time raster + manifest

### Authoring rules

1. **Put the name in `id`, never `inkscape:label`.** Saving as Plain SVG strips
   the `inkscape:` namespace and the labels with it
   ([Inkscape wiki](https://wiki.inkscape.org/wiki/index.php/Inkscape_SVG_vs._plain_SVG)).
2. **Never "Optimized SVG".** It runs `scour`, whose `--shorten-ids` and
   `--enable-id-stripping` will eat the ids, and the "preserve IDs starting
   with" option has a [known bug](https://gitlab.com/inkscape/extensions/-/work_items/436).
3. **Root `width`/`height` numerically equal to the `viewBox`, origin at 0.**
   Then `png_px = user_unit × (png_width / viewBox_width)` exactly
   ([Units in Inkscape](https://wiki.inkscape.org/wiki/Units_In_Inkscape)).
4. **A separate invisible `anchors` layer** of small stroke-less circles,
   `id="anchor-btn-a"`. This sidesteps the visual-vs-geometric bounding box
   question entirely: a stroke-less circle has the same bbox either way, and the
   anchor is decoupled from the button's visual extent.
5. **No `<text>`** — pygame draws the labels.

ids must be unique, must not start with a digit, and cannot contain whitespace
([MDN](https://developer.mozilla.org/en-US/docs/Web/SVG/Attribute/id)).

### Verified locally

Everything below was run, not cited.

```
resvg                     0.48.1     in nixpkgs
inkscape                  1.4.4      in nixpkgs
librsvg                   2.62.3     in nixpkgs
python3Packages.pygame-ce 2.5.8      what src/ui/default.nix already uses
```

**`load_sized_svg` does work in this closure** (pygame-ce 2.5.8, SDL 2.32.70,
SDL_image 2.8.12) — it needs pygame-ce ≥ 2.4.0 and SDL_image ≥ 2.6.0
([pygame-ce docs](https://pyga.me/docs/ref/image.html)), and both are satisfied.
But the documented aspect-ratio clamp is real and reproducible:

```
requested (800, 400) -> (800, 400)
requested (1600, 900) -> (1600, 800)     <- height clamped
requested (600, 600) -> (600, 300)       <- height clamped
```

You cannot trust the size you asked for, which silently breaks any coordinate
mapping computed from it. That, plus NanoSVG being documented as "limited
support" ([pygame docs](https://www.pygame.org/docs/ref/image.html)), is why
runtime SVG loses to build-time rasterisation here.

**The full pipeline was tested end to end.** A probe SVG with two `anchor-*`
circles, rasterised by resvg at 3×, anchors extracted with `xml.etree` and
normalised against the viewBox, then each anchor's pixel sampled out of the PNG:

```
anchors (normalised u,v): {'btn-a': (0.75, 0.6), 'btn-b': (0.85, 0.4)}
rasterised PNG: 1200x600  (SVG viewBox 400x200)
  btn-a  -> px( 900,360) = rgb(204, 51, 51)  HIT
  btn-b  -> px(1020,240) = rgb(51, 204, 51)  HIT
```

Normalised `u,v` is the key detail: one manifest serves every density tier, so a
whole class of drift is structurally impossible.

### Recommended pipeline

**Build (Nix derivation):** for each controller SVG, `resvg --width {W} … .png`
at 1×/2×/3×, plus one stdlib Python script that parses the SVG once and writes
`anchors.json` with normalised coordinates and the SVG's SHA-256.

**Runtime (pygame, zero SVG deps):** load the nearest PNG tier,
`smoothscale` down, `anchor_px = (u × surface_w, v × surface_h)`.

`resvg` is the right rasteriser: a single ~5 MB static Rust binary with no
system-library closure, ~1600 conformance tests
([resvg](https://github.com/linebender/resvg)). Rejected: cairosvg (system
cairo + cffi, SVG 1.1 only), svglib (weakest fidelity), Inkscape CLI (drags in
GTK at build time).

**Coordinate extraction** needs no dependency — `<circle cx cy>` anchors in a
transform-free layer are readable with `xml.etree`. If the anchors ever end up
inside transformed groups, either `inkscape --query-all` (which prints
`id,x,y,width,height` for every identified object, and note the CLI changed
incompatibly from 0.92 to 1.x — `-z`, `-f` and `-e` are all gone) or the pure-Python
`svgelements` will resolve the matrix cascade.

## 3. Layout: two-sided boundary labeling

The formal name is **boundary labeling**, introduced by Bekos, Kaufmann,
Symvonis and Wolff (Computational Geometry 36(3), 2007), and it is motivated in
the original paper by exactly this use case — "technical drawings and
illustrations in medical atlases"
([KIT project page](https://algo.iti.kit.edu/en/projects/geovis/boundary)).

**Leader taxonomy** ([External Labeling survey, arXiv:1902.01454](https://ar5iv.labs.arxiv.org/html/1902.01454)):
a leader is a string over segment orientations, `o` = orthogonal to the label
edge, `p` = parallel, `s` = free slope.

- **type-po** — one bend: vertical run, then horizontal into the label.
- **type-opo** — two bends: out of the button, a vertical run confined to a
  *track routing area*, then into the label. **This is the one to use** — the
  track area guarantees no leader ever crosses the artwork.
- Both cost the same: the leader length is the Manhattan distance either way.

**The key result: sorting is optimal.** For one side, matching anchors to slots
in y-order simultaneously minimises total leader length and yields a
crossing-free layout. The horizontal component is identical for every
assignment, so the problem reduces to minimising `Σ|anchor_y − slot_y|` — a 1-D
transportation problem whose optimum is the monotone matching. And sorted order
*is* non-crossing, since two leaders on a rail cross exactly when their vertical
order is inverted. Bekos et al.'s original O(n²) was improved to **O(n log n)**
by Benkert et al.'s sweep. Minimising *crossings* in general is NP-hard — but
you never need to, because on one side you get it free.

**What not to use.** Simulated annealing (Christensen–Marks–Shieber 1995, and
its canonical implementation [D3-Labeler](https://github.com/tinker10/D3-Labeler))
genuinely won that paper's empirical study and is right for hundreds of point
features — but it is stochastic, so labels jitter between runs. For n ≤ 14 on
two rails the problem is exactly solvable. Hungarian matching computes the same
answer a sort gives, at O(n³).

### The algorithm

1. **Side assignment** — `LEFT if anchor_x < device_centre_x else RIGHT`, which
   is what [ECharts' pie label layout](https://github.com/apache/echarts/blob/master/src/chart/pie/labelLayout.ts)
   does. Two gamepad-specific fixes: hard-pin shoulders/triggers to their
   obvious side and force them to the top slots, and rebalance by moving the
   anchor nearest the centre line when one side overflows.
2. **Sort each side by `anchor_y`.** This is the whole optimality argument.
3. **Seed** each label at `y = anchor_y − h/2` (a perfectly horizontal leader),
   then run ECharts' `shiftLayout`: a forward pass pushing overlaps down, then
   redistribute from the opposite bound, then squeeze the padding, then spread
   the residual. Every step is a monotone shift on a sorted list, so **order is
   preserved and the layout stays crossing-free**.
4. **Draw the opo leader** — `(ax,ay) → (elbowX,ay) → (elbowX,label_y) →
   (railX,label_y)`, with `elbowX` in the gutter.

**Test it:** the algorithm is provably crossing-free, so a test asserting zero
segment intersections over a set of anchor configurations catches any bug in the
side-assignment or shift pass.

### Does Steam do this?

Steam's configurator *does* draw leader lines — "lines connecting the bindings
and input styles to help locate which ones correspond to what part of the
controller", which highlight on hover
([Steam Input Wiki](https://steaminput.wiki/en/intro/configurator)). Whether the
layout is computed is a different question, and the evidence says no: the
controller `.vdf` files hold binding data with no UI geometry, the client UI is
Panorama CSS, glyphs are authored assets, and unrecognised controllers fall back
to a fixed generic template that the user maps onto. **It appears hand-authored
per controller model** — a well-supported inference, not a verified fact.

That is also the right call for Valve, and worth noting for us: with a fixed
layout the UI never reflows when a binding changes, which matters for
controller-driven focus navigation. Our per-console anchor manifest is
effectively the same thing — hand-authored positions — with the *label* side
solved algorithmically.

## Key takeaways

1. **Draw the controllers.** No permissive source covers N64 or Mega Drive at
   all, and the two CC0 files that exist have no semantic ids and are full of
   gradients, blur filters and unrenderable `flowRoot` text.
2. **CC BY-SA art is a trap** — adaptation triggers share-alike, and it gives
   zero trademark cover anyway. Flat, unbranded line art is both the licence
   answer and the trademark answer.
3. **Rasterise at build time with resvg**, ship PNGs plus a normalised-coordinate
   manifest. Runtime stays pygame-only. Verified working end to end.
4. **`load_sized_svg` exists here but clamps aspect ratio** — measured, not
   assumed. Another reason to pre-rasterise.
5. **Sort by y within each side.** That single line is provably both
   length-optimal and crossing-free; everything else is overlap resolution.
6. **Use opo leaders with the vertical run in the gutter**, so a leader can
   never cross the artwork.

## Method

Three parallel research agents (artwork/licensing, SVG toolchain, label-placement
algorithms) across ~45 sources, then four verifications run locally in this
repo's own closure rather than taken on citation: the three Commons SVGs
downloaded and DOM-parsed; nixpkgs versions for resvg/inkscape/librsvg/pygame-ce
queried; `load_sized_svg` availability and its aspect-ratio clamp measured; and
the resvg → anchor-manifest → pixel-check pipeline run end to end.

Unresolved: ES-DE's `resources/graphics/help/*.svg` content (project is MIT, tree
not opened); Nintendo design-patent expiry for retro-era controllers; whether
Inkscape's `--query-*` returns visual or geometric bboxes (moot under the
`anchor-*` circle approach).
